# HMMWV 교범 파싱·전처리 검증 결과

이 문서는 최초 501쪽 OCR 처리의 기록이다. 이후 전체 PDF의 이미지·문자 매핑 오류까지 확장한 최신 결과는 [전체 교범 파싱 검토 결과](전체교범_파싱_검토결과.md)에 있다.

작성일: 2026-09-22

## 결론

**이 교범은 PyMuPDF의 텍스트 추출만으로 충분히 복원되지 않는다. 그렇다고 LLM이 필수인 것도 아니다.** 원래 텍스트층은 PyMuPDF로 읽고, 이미지에 들어 있는 문자는 일반 OCR로 읽을 수 있다. 실제로 LLM 없이 추출 프로그램을 구현해 실행했다.

다만 두 가지 한계를 확인했다. OCR에는 글자 오인식이 있으며, OCR을 새로 계산할 때 일부 결과가 달라졌다. 따라서 현재 확인한 재현성은 **원본 PDF와 고정된 OCR 추출본을 입력으로 전처리를 다시 수행하는 범위**다. PDF만으로 OCR까지 매번 새로 계산했을 때 모든 문자가 같다는 결과는 아니다.

고정 OCR 추출본을 사용한 독립 실행 두 회에서는 **29개 산출물의 SHA-256이 모두 일치했고, 각 실행의 자동 검사 30개가 모두 통과했다.** 원시 OCR 자료는 아직 내용 검수 전이다. 최종 RAG corpus나 60개 질의의 정답 근거 대응표를 확정한 것은 아니다.

## PyMuPDF만으로 추출하면 생기는 문제

PDF에는 원래 텍스트와 이미지가 혼합되어 있다. 문서번호·쪽번호가 읽힌다고 본문까지 읽힌 것은 아니다.

- PDF 97·103·111쪽은 정비 점검표 자체가 이미지다. 예를 들어 97쪽의 원래 본문 추출량은 84자에 불과해, OCR 없이 읽으면 대부분의 점검 내용이 빠진다.
- PDF 100쪽의 표는 문자가 직접 추출되지만, 일반적인 표 인식만으로는 절차와 운행 불가 판정 조건이 섞이는 문제가 있었다. 구현한 열별 추출에서는 `Do not clean CDR valve with solvent.`와 CDR 진공시험 실패 조건을 서로 다른 열로 보존했다.
- PDF 180·500·610·860쪽과 같은 회로도·고장진단도는 OCR로 글자를 읽어도 연결선과 YES/NO 분기의 의미를 자동으로 확정할 수 없다.
- PDF 111쪽의 OCR에서는 `lb-ft`가 `Ib-ft`로 읽히는 사례가 있다. PDF 103쪽의 일부 셀은 오인식이 더 크다. 이런 결과를 검수 없이 최종 근거로 채택하지 않았다.

자세한 예시는 [표본 원문 대조 기록](표본_원문대조_기록.md)과 [원문 대조 HTML](output/run-a/검토용_원문대조.html)에 있다. HTML은 원본 페이지와 추출 결과를 나란히 보여준다.

## 처리한 범위와 산출물

| 항목 | 결과 |
| --- | ---: |
| 원본 PDF 전체 | 890쪽 |
| 연구 범위인 제1·2장 | PDF 31~863쪽, 833쪽 |
| 범위 내 이미지 포함 페이지 | 665쪽 |
| 머리말 등을 제외한 원래 텍스트가 남는 페이지 | 794쪽 |
| 일반 OCR을 적용해 추출본을 만든 페이지 | 501쪽 |
| PMCS 점검표의 분리된 행·상단 안내 구간 | 55개 |
| 그중 이미지 표에서 OCR한 행 | 6개, PDF 97·103·111쪽 |
| 원본이 빈 페이지 | PDF 570쪽 |
| 원문 대조 HTML의 원본 페이지 | 18쪽 |

OCR 대상은 ‘원래 본문이 350자 미만이며 이미지가 있는 페이지’와 지정한 비교용 페이지다. **501쪽 모두가 OCR을 반드시 필요로 한다는 분류 결과는 아니다.** 반대로 350자 이상 추출되는 페이지라도 이미지 속 글자가 빠질 수 있어, 이미지 포함 페이지 전체를 검토 대상으로 표시했다.

표·본문·OCR 결과에는 PDF 순번과 원문 좌표를 남겼다. 쪽번호의 글자 사이 공백과 빈 면을 함께 표시한 형식을 처리했다. 제2장 범위의 PDF 810쪽에는 원본에도 `3-710`이 인쇄되어 있어 이를 그대로 보관하고 예외로 표시했다. 프로그램이 임의로 `2-710`으로 바꾸지 않았다.

## 재현성 검증

### 원본 PDF에서 OCR을 새로 계산

초기 PyMuPDF 내장 OCR을 포함한 독립 전체 실행에서 22쪽의 OCR 결과가 달랐다. 스레드 설정, 별도 프로세스, 독립 Tesseract 빌드와 고정 내적 연산 등을 적용한 추가 검사에서도 일부 문자·신뢰도 수치 차이가 남았다. 따라서 이 경로의 완전한 일치는 확인하지 못했다.

입력 이미지가 같은데 OCR 결과가 달라지는 사례도 확인했다. 엔진 내부의 구체적인 결함 원인까지 입증한 것은 아니다. 실패한 검사를 성공으로 처리하거나, 차이가 난 문자를 임의로 삭제하지 않았다.

근거: [초기 전체 비교 결과](audit/verification_initial.json), [후속 단계별 비교 기록](audit/ocr_stage_probe.json), `audit/generic-capture-partial/`.

### 고정 OCR 추출본을 이용한 전처리

완료한 OCR 실행 결과를 `assets/ocr-snapshot/`에 보관했다. `replay.py`는 다음 작업을 다시 수행한다.

1. 원본 PDF와 설정·OCR 추출본의 해시를 확인한다.
2. 원래 텍스트층과 좌표를 전체 PDF에서 다시 읽는다.
3. OCR 대상 501쪽을 다시 렌더링해 고정 추출본을 만들 때의 픽셀 해시와 대조한다.
4. 고정된 OCR 문자를 사용해 형식 정리·표 열 분리·출처 기록·근거 문구 검사·확인용 자료 생성을 다시 수행한다.

| 검사 | 결과 |
| --- | --- |
| 독립 재실행 두 회 | 둘 다 정상 완료 |
| 파일별 SHA-256 비교 | **29/29 일치** |
| 자동 검사 | **각각 30/30 통과** |
| 새 OCR 계산 | 없음. 명시적으로 고정 추출본을 사용 |
| 원본 PDF 재추출 및 이미지 해시 대조 | 수행 |
| LLM·외부 생성형 AI API 호출 | 없음 |

근거: [최종 검증 JSON](audit/verification.json), [실행 기록](audit/replay_execution.json), [산출물 해시 목록](output/run-a/manifest.json).

검증 환경은 Windows x64, Python 3.11.9, PyMuPDF 1.28.2다. 고정 추출본을 만들 때 사용한 OCR은 tesserocr 2.10.0 / Tesseract 5.5.2와 해시를 고정한 영어 언어 데이터다. 패키지와 모델·설정·코드 해시는 각 manifest에 남겼다. 이 검사는 OCR의 문자 정확도 평가나 RAG 성능 평가가 아니다.

## 평가질의에 미치는 영향

60개 후보의 근거 위치 101건 중 검색 범위 안의 91건은 모두 **지정된 근거 문구가 원래 텍스트층에서 발견**됐다. 나머지 10건은 권별 구성을 확인하기 위한 PDF 20쪽으로, 검색 범위 밖이다.

이 결과만으로 60문항을 그대로 확정할 수는 없다. 짧은 문구나 절 번호가 있다는 것과 질문에 필요한 설명·조건·단위가 충분히 복원됐다는 것은 다르다. 특히 표의 열 연결과 그림 속 설명을 확인해야 한다. 해당 검사 결과는 `candidate_anchor_audit.jsonl`에 저장했고, 정답 충분성은 `NOT_VERIFIED`, 최종 청크 대응은 `PENDING`으로 남겼다.

다음 작업은 **현재 후보가 참조하는 범위 내 47쪽의 필수 근거부터 원문 대조**하는 것이다. 그 밖의 corpus도 같은 처리 규칙으로 검수하고, 표·경고·연속 항목의 연결을 정한 뒤 기존 규칙의 500 token / 같은 단위 내 100 token 중첩으로 청킹한다. 이번 작업에서는 청킹·임베딩·RAGAS 평가를 진행하지 않았다.

## 실행 방법

현재 환경에서 재현할 때는 [README](README.md)의 `replay.py` 명령을 사용하면 된다. 원본부터 OCR을 새로 계산하는 `preprocess.py`와 새 추출본을 버전으로 보관하는 `freeze_ocr.py`도 함께 제공했다.

LLM을 도입할 필요는 없다. 현재 필요한 것은 OCR의 오인식과 표·그림 의존 구간을 원문에 맞게 검수하고, 연구에 사용할 데이터 버전을 확정하는 일이다.
