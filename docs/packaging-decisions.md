# GitHub 준비본 결정 기록

작성일: 2026-09-29. 범위는 기존 실험의 배포용 복사본과 재연 도구입니다. 원 연구 디렉토리의 계산 코드·결과를 변경하지 않습니다.

## P01. 기존 경로와 바이트 유지

- 맥락: corpus·검색·생성·평가가 입력과 코드의 SHA-256 및 상대 경로를 검증합니다.
- 검토: 일반적인 `src/data/results` 구조로 전면 이동하거나, 원래 경로를 보존하고 최상위 안내를 추가할 수 있습니다.
- 결정: `preprocessing/retrieval/experiment` 구조와 기존 파일 바이트를 보존합니다. `.gitattributes`에서 자동 줄바꿈 변환을 막습니다. 공개 전 검토 후 승인된 경로·문서 메타데이터 정리의 범위와 원본 보존은 아래 P11에 추가했습니다.
- 이유: 경로 이동·줄바꿈 변경만으로도 원 실험의 검증 계약이 깨집니다.
- 영향: artifacts/original-files.json, .gitattributes, README.md.
- 후속 검토: 추후 구조 개편은 별도 버전으로 하고 원본 보존 검증과 분리합니다.

## P02. Git 파일과 자료 ZIP 분리

- 맥락: 앱·결과는 작지만 OCR·corpus·벡터·캡처에는 큰 파일과 많은 바이너리가 있습니다.
- 검토: 모두 Git에 저장, LFS 사용, 작은 기록은 Git·고정 자료는 Release 첨부로 분리.
- 결정: 코드·원 평가/생성 기록은 Git 후보에, 큰 재연 자료는 runtime-data / preprocessing-replay / review-evidence ZIP으로 분리합니다. 모델 가중치·가상환경은 설치 시 생성합니다.
- 이유: 소스 검토와 버전 관리가 쉬우며, 자료를 해시로 고정해 복원할 수 있습니다.
- 영향: artifacts/manifest.json, .gitignore, scripts/restore_artifacts.py.
- 후속 검토: 실제 Release 업로드 후 검증한 URL을 별도 기록합니다. 현재 URL은 미지정입니다.

## P03. 실패 기록과 필요한 백업 포함

- 결정: 새 도구가 지정된 부모 평가와 해당 생성 실행을 대조하고 gold-v2를 적용한 입력·출처·도구 해시를 고정합니다. run 단계는 기존 엔진입니다.
- 이유: 새 답변을 준비했다고 생각하면서 원 실험 답변을 평가하는 문제를 방지합니다.
- 영향: scripts/prepare_revised_evaluation.py, docs/reproduction.md.
- 후속 검토: 출처가 다른 답변·미완료 부모·다른 평가 설정은 거부합니다. 이 준비 단계는 API를 호출하지 않습니다.

## P10. 고정 OCR 재생의 메타데이터 차이

- 맥락: 추출 재연 양쪽은 원 검증의 27개 검사를 통과하고, 30개 파일 중 29개가 바이트 단위로 같았습니다. manifest에서 과거 OCR worker 해시 한 필드만 달랐습니다.
- 검토: 과거 파일을 현재 해시로 바꾸기, 현재 코드를 과거 상태로 바꾸기, 내용 일치와 메타데이터 차이를 분리해 기록하기.
- 결정: 원본을 유지하고 scripts/verify_parse_replay.py에서 엄격한 예외 하나만 검사합니다. 다른 29개 파일·나머지 manifest 값이 같고, 새 OCR 계산이 없고, 새 worker 해시가 현재 파일과 일치해야 합니다.
- 이유: 현재 고정 OCR 재생에서 사용하지 않는 worker의 이력을 숨기지 않으면서 본문 재연 여부를 확인할 수 있습니다.
- 영향: scripts/verify_parse_replay.py, docs/reproduction.md, 새 로컬 검증 보고서.
- 후속 검토: 다른 필드나 본문이 달라지면 실패로 처리합니다. 전체 30개 파일이 바이트 단위로 일치했다고 보고하지 않습니다.

- 결정: 실험 문서 37개와 보고서·화면 파일 8개의 설명을 정리했습니다. 지표 정의·근거·시점·실행 상태·평가 수치는 유지하고, 연결할 수 없는 문서 참조와 작성 메모를 제거하거나 실험 설명으로 바꿨습니다. 보고서 생성기의 문자열에도 같은 변경을 적용했습니다.
- 이유: 문서를 별도로 해석할 자료 없이 읽을 수 있고, 보고서를 재생성해도 같은 설명을 얻을 수 있습니다. 원 연구 폴더와 수정 전 공개본은 저장소 밖에 보존합니다.
- 영향: README와 배포 안내, research/preprocessing/retrieval/experiment의 관련 문서, 보고서 생성기·HTML, 활성 검증 목록 3개, review-evidence ZIP, publication-changes와 manifest.
- 후속 검토: Git·ZIP의 Markdown 전체와 보고서·화면 문구를 검색하고 문맥을 확인합니다. 변경하지 않은 연구 자료의 바이트 보존, 활성 입력 해시, ZIP 파일 목록·해시와 보고서 생성기의 문자열 외 코드 불변을 검증합니다. 과거 출처 해시는 보존하고 현재 공개 사본의 해시는 별도로 기록합니다.

## P16. 공개 저장소와 고정 Release 게시

## P19. 게시 시점의 저장소 공개 상태 확인

- 맥락: 2026-09-30 게시 직전 GitHub API에서 저장소가 private인 것을 확인했다. 사용자는 public 저장소와 정정 내역을 포함한 새 버전 공개를 요청했다.
- 검토: private 상태로 배포하거나, 검증한 정정본·첨부 자료를 준비한 뒤 public으로 전환.
- 결정: 정정 커밋과 Release 첨부를 준비한 뒤 저장소를 public으로 전환하고 새 Release를 게시한다. 저장소·태그·과거 첨부·커밋 이력은 삭제하지 않는다.
- 이유: 요청한 공개 재현 자료를 로그인 없이 받을 수 있어야 한다.
- 영향: GitHub 저장소 visibility, Release 본문과 첨부, 게시 후 검증 기록.
- 후속 검토: 비인증 Git clone·Release 다운로드와 복원 검사를 실시하고, 과거 태그·첨부의 동일성을 확인한다. 공개 상태가 이전과 달라진 원인은 이 작업에서 추정하지 않는다.
