# 검색용 corpus 생성과 청킹 구현 계획

조사 시작: 2026-09-23. 계획 작성: 2026-09-24. 공개 저장소의 문서·관련 구현을 조사하고 현재 교범 자료에 적용할 방식을 정리했다. 아래 프로그램과 산출물은 구현 계획이다. 이번 조사에서는 외부 코드를 실행하거나 패키지를 설치하지 않았다.

**권고하는 방식**

IBM Research에서 시작한 Docling의 문서 구조·출처 관리 방식과 Microsoft Azure 예제의 청킹·검증 사례를 참고하여, 기존 v4 보정 자료를 입력으로 사용하는 Python 명령행 프로그램을 만든다. 원문 구간 선택, 구조 구성, 청킹, 검증을 별도 단계로 분리한다. 기존에 확보한 Qwen tokenizer와 보정·검증 자료를 재사용한다.

Docling의 구조 중심 접근은 적합하지만, 그 청커의 기본 동작이 현재 실험 규칙과 같지는 않다. DoclingDocument로 변환하는 어댑터에 더해 고정 중첩·구간별 보정 이력 처리가 필요하므로, 이번 교범에는 기존 JSONL 레코드를 직접 다루는 작은 프로그램이 더 단순하다고 판단했다. 이는 저장소의 우열이나 성능 비교 결과가 아니라 현재 입력과 실험 규칙에 대한 설계 판단이다.

- `DocMeta`는 제목과 원문 문서 항목을 함께 보관한다. 검색 텍스트와 출처 메타데이터를 구분하는 방식이 유용하다. [자료형 구현](https://github.com/docling-project/docling-core/blob/876e9d8852b56a1345cfbba4aaa6baa6dc9941e0/docling_core/transforms/chunker/doc_chunk.py)

- 긴 표의 머리글 반복과 본문 보존을 확인하는 테스트가 있다. 우리 검증에서도 표가 나뉜 뒤 조건과 값의 관계가 남는지 확인한다. [표 관련 테스트](https://github.com/docling-project/docling-core/blob/876e9d8852b56a1345cfbba4aaa6baa6dc9941e0/tests/test_hybrid_chunker.py#L510-L627)

그대로 쓰기 어려운 차이도 확인했다. Docling HybridChunker는 기본적으로 `merge_peers=True`이고 본문의 고정 100 token 중첩을 적용하는 구현이 아니다. 제목 등의 길이 때문에 본문 예산이 사라지면 제목·캡션을 제거하고 재분할하는 경로도 있다. 우리 규칙에서는 필요한 맥락을 자동으로 버리지 않고 오류로 남겨야 한다. [해당 구현](https://github.com/docling-project/docling-core/blob/876e9d8852b56a1345cfbba4aaa6baa6dc9941e0/docling_core/transforms/chunker/hybrid_chunker.py)

Azure 예제의 기본 500이라는 수치만 보고 동일한 청킹이라고 해석해서는 안 된다. tokenizer가 다르고, 중첩은 고정 100 token이 아니며, 그림이 있는 청크에는 길이 예외가 있다. 기존 실험의 500/100은 유지하되, 이를 공개 저장소가 입증한 최적값이라고 표현하지 않는다. 원본은 제1권의 1996년 발행·2004년 Change 2 반영 PDF이며, 검색 범위는 PDF 순번 31~863쪽의 제1·2장 833쪽이다. 전체 890쪽에서 추출한 자료는 보존한다. 60문항에 필요한 부분만 골라 corpus를 만들지 않는다. 문자로 처리 가능한 본문·표를 포함하고, 범위 밖 자료와 그림 해석이 필요한 내용은 별도 사유로 구분한다.

기존의 구간별 판정 557건이 833쪽 전체의 완성된 선택 지도라는 뜻은 아니다. corpus 구성에서는 나머지 구간에도 채택·중복·제외·검토 필요 여부를 부여해야 한다. 기존에 검토를 끝낸 구간은 해당 판정을 재사용한다.

**3. 프로그램의 처리 순서**

`고정한 보정·구조 자료 → 구간 선택 기록 → 구조화 corpus → 500/100 청크 → 독립 검증 → 검색 입력본 고정`

**단계 A — 입력 확인과 구간 선택**

입력 파일·설정·tokenizer의 해시를 확인한다. native와 OCR은 같은 내용의 대안 추출층이므로 대응 구간에서는 하나만 채택한다. 557건의 규칙은 지정된 구간에만 적용하며, 페이지 전체를 native 또는 OCR로 일괄 교체하지 않는다. native에는 참조문만 있고 이미지 안에 본문이 있는 구간은 검토된 OCR 본문을 보존한다.

각 구간에 다음 중 하나의 상태와 사유를 기록한다: `INCLUDED`, `DUPLICATE_ALTERNATIVE`, `EXCLUDED_BY_SCOPE`, `EXCLUDED_NON_TEXT`, `LAYOUT_ONLY`, `NEEDS_REVIEW`. 중복은 같은 원문 위치의 대안 추출인지로 판정한다. 서로 다른 정비항목에 반복된 동일 경고문은 단순 문자열 중복이라는 이유로 삭제하지 않는다.

833쪽의 페이지별 처리표를 만들고 모든 원문 텍스트 후보 및 이미지 영역이 어떤 상태로 처리되었는지 연결한다. 의도적으로 빈 페이지는 빈 페이지로 기록한다. 페이지 수가 일치하는 것과 본문이 빠짐없이 들어간 것은 별도로 검사한다. 규칙이 없거나 서로 충돌하는 구간은 검토 목록에 남기며, 이를 무시하고 corpus를 확정하지 않는다.

**단계 B — 구조와 읽기 순서 구성**

장·절·정비작업·고장진단 항목·독립 하위 항목의 계층을 만든다. 제목 인식은 번호·좌표·기존 구조 자료를 사용하고, 모호한 경계는 근거 위치와 함께 검토 대상으로 남긴다. 같은 항목의 페이지 간 연결은 항목 식별자와 확인된 연결에 따른다. 다음 페이지가 소문자로 시작한다는 이유만으로 합치지 않는다.

머리말·쪽번호 제거, 줄 결합, 줄끝 하이픈 처리 등은 변경 전후와 출처를 기록한다. 하이픈을 일괄 삭제하지 않는다. 값·단위·적용 차종·부정문·절차 순서와 경고의 적용 범위를 보존한다. 새 문자 오류가 발견되면 corpus 코드에서 몰래 고치지 않고 보정 목록의 다음 버전으로 처리한다.

각 구조단위에는 본문뿐 아니라 적용되는 제목·경고·조건의 원문 참조를 저장한다. 이를 곧바로 평가용 근거 단위나 질의 유형으로 간주하지 않는다. Oracle Evidence의 정의는 기존 평가 규칙을 따른다.

**단계 C — 표와 그림 주변 문자 처리**

PMCS는 셀·행·항목 연결과 경고 연결 자료를 적용한다. 표는 원문의 열 이름과 값이 연결되도록 직렬화한다. 표 제목·행 식별자·단위·차종·적용 조건은 관련 값과 함께 유지한다. 빈 셀을 임의의 값으로 채우지 않는다. 앞 행·앞 페이지의 값을 이어 받는 경우도 원문에서 확인된 연결을 사용한다.

표 전체를 무조건 하나의 청크로 만들지 않는다. 독립적으로 읽을 수 있는 행·하위 항목은 구조상 경계로 삼고, 긴 절차 셀을 나눌 때에는 항목과 열 이름, 필요한 조건을 반복한다. 다른 행의 값이 잘못 연결되지 않게 셀별 출처를 유지한다. 독립적인 의미 경계가 불명확하면 행마다 강제로 자르지 않고 검토한다. 표 4개·33행 외에도 기존 복원 표와 표 후보 분류 자료를 모두 반영해야 한다.

문자만으로 뜻이 확인되는 이미지 내 설명·표는 채택할 수 있다. 그림·회로·화살표 관계의 새로운 해석이나 LLM 설명문은 만들지 않는다. 고장진단 흐름도는 확인된 문자와 명시적 참조를 보존하되, 확인되지 않은 분기 관계를 문장으로 조립하지 않는다. 그림을 봐야 성립하는 정보는 해당 사유와 원문 위치를 남긴다.

PDF 118쪽의 불완전한 `Metal particles are`는 원문 문제 표시와 함께 보존한다. 해당 문장을 완성하거나 충분한 정답 근거로 단독 사용하지 않는다. 이 문제 때문에 같은 페이지의 정상적인 다른 지시문까지 제외하지 않는다.

**단계 D — Qwen tokenizer로 청킹**

1. 구조단위의 제목·조건·필요한 표 설명과 본문을 구분한다. 청크에 실제로 들어갈 전체 검색 문자열을 조립하고 Qwen tokenizer로 계수한다. tokenizer의 자동 잘림과 특수 token 추가는 끈다.
2. 전체가 500 token 이하면 그대로 하나의 청크로 만든다. 짧다는 이유로 다른 구조단위와 합치지 않는다.
3. 넘으면 같은 구조단위의 본문을 token 창으로 나눈다. token의 문자 위치를 추적하여 원문 문자가 손상되지 않는 경계에서 자른다. 창의 후보 길이를 정한 뒤 제목·반복 설명까지 붙인 최종 문자열을 다시 계수한다. 부분별 token 수의 단순 합을 최종 길이로 대신하지 않는다.
4. 인접 창에는 본문 100 token을 중첩한다. 문자 경계를 보정해야 할 때에는 100 token 이상이 되는 가장 짧은 중첩 구간을 사용하고 실제 수를 저장한다. 반복한 제목·표 머리글은 본문 중첩 수에 포함하지 않는다. 단위 전체가 한 청크에 들어가는 경우와 서로 다른 구조단위 사이에는 중첩하지 않는다.
5. 다음 창이 새 본문을 추가하는지 검사한다. 조건과 제목이 너무 길어 500 제한·본문 중첩·진행을 함께 만족할 수 없으면 오류로 기록하고 완료 처리를 중단한다. 자동 요약, 조건 삭제, 제한 초과 허용으로 통과시키지 않는다.
6. 원문 순서대로 `C000001`부터 ID를 부여하고 corpus 버전·설정과 함께 고정한다. 입력이나 설정이 바뀌면 새 버전과 ID 대응표를 만든다.

이 계획은 Azure의 문장 경계 알고리즘을 그대로 도입하여 고정 token 창 규칙을 바꾸는 것이 아니다. 문장·페이지 경계 사례는 읽기 순서와 문자 보존 검사에 참고한다. 더 의미 있는 문장 단위 분할을 별도 실험으로 추가하려면 방법 변경으로 기록한다.

청크는 Qwen 기준 500 token으로 관리하지만 임베딩 모델 BGE-M3의 tokenizer는 별개다. 후속 임베딩 단계에서는 같은 검색 문자열이 BGE-M3 입력에서 잘리지 않는지도 따로 검사한다. 출처 ID와 chat template을 포함한 전체 LLM 입력 길이 역시 후속 생성 단계에서 검사한다.

**단계 E — 독립 검증과 재현 확인**

생성 프로그램이 작성한 ‘정상’ 표시만 읽는 검증은 피한다. 검증 프로그램은 원본 입력·채택 규칙·문자 위치와 산출물을 다시 읽어 다음 조건을 계산한다.

| 검사 | 통과 기준 |
| --- | --- |
| 범위와 누락 | 833쪽 모두 처리표가 있고, 선택된 본문·셀은 청크 본문 또는 기록된 반복 맥락에 대응한다. 허용된 형식 정리 외에 설명되지 않은 누락이 없다. 범위 안의 의미 있는 문자 추출 실패를 제외 사유로 숨기지 않는다. |
| 변경 추적 | 청크의 문자 구간은 보정본 또는 기록된 제목·조건 복사에서 재구성된다. 줄바꿈·구분자 등 직렬화용 문자열은 별도 유형으로 표시한다. 요약·새 사실·기록 없는 문자 변경이 없다. |
| 중복과 순서 | 같은 위치의 native/OCR 중복 채택이 없다. 표 행·열과 페이지 간 연결이 지정 규칙과 맞는다. 의도한 overlap·제목 반복은 별도로 집계한다. |
| 길이와 경계 | 최종 검색 문자열의 Qwen 길이가 모두 500 이하이고, 본문 중첩·새 본문 진행·문자 보존 조건을 만족한다. 구조단위를 넘는 overlap이 없다. |
| 표·조건 | 셀 값, 열 제목, 단위, 적용 차종, 경고와 본문의 연결이 유지된다. 표를 분할해도 관련 조건의 출처가 남는다. |
| 검토 상태 | 선택이나 구조에 관한 미결 `NEEDS_REVIEW`가 0이다. 원문 자체의 알려진 오타·불완전 문장은 ‘해결됨’으로 지우지 않고 별도 상태로 남긴다. |
| 재현 | 동일한 입력·규칙·환경으로 두 번 실행한 corpus·청크·매핑 파일의 해시가 일치한다. 실행시각 등은 별도 실행 기록에 둔다. |

기계 검사는 선택 규칙의 적용·문자 보존·출처 추적을 검증한다. 의미 관계의 정확성은 원문 이미지 대조가 필요하므로 본문·표·고장진단 유형의 표본과 검토 목록을 확인한다. 구현 후에는 기존 계획대로 최종 평가질의의 모든 필수 근거도 원문과 대조한다. Codex의 확인과 연구자의 직접 확인은 별도 상태로 남긴다.

**4. 파일과 실행 인터페이스 계획**

새 프로그램은 `<PROJECT_ROOT>/preprocessing/corpus/` 아래에 둔다. 다음 이름은 아직 생성하지 않은 제안이다.

| 모듈 | 책임 |
| --- | --- |
| `build.py` | 고정 입력 확인, 실행 순서, 새 출력 폴더 관리 |
| `select_spans.py` | native/OCR 선택, 중복 구간 및 포함·제외 기록 |
| `structure.py` | 제목 계층, 읽기 순서, 항목·표·경고 연결 |
| `serialize.py` | 본문·표를 검색 문자열로 만들고 문자 출처 매핑 |
| `chunk.py` | Qwen 계수, 500/100 분할, ID 부여 |
| `verify.py` | 입력과 산출물을 별도로 읽는 보존·경계·재현 검사 |

설정에는 PDF 범위, 입력 경로·해시, tokenizer revision·해시, 500/100, 문자열 직렬화 버전과 정렬 기준을 넣는다. Python 표준 라이브러리와 기존 환경의 `tokenizers`를 기본으로 사용한다. 재현용 실행에는 LLM이나 GPU가 필요하지 않다. 새 검토가 필요한 구간에 대한 원문 판단은 기록으로 확정한 뒤 다시 실행한다.

출력은 새 폴더에 생성하며 다음 자료를 제공한다.

| 산출물 | 내용 |
| --- | --- |
| `corpus_units.jsonl` | 청킹 전 구조단위·제목·본문·표·조건 |
| `chunks.jsonl` | 청크 ID, 최종 검색 문자열, token 수, 구조단위 ID, 본문 위치, 실제 overlap |
| `source_map.jsonl` | 출력 문자 위치 → 보정 레코드 위치 → 원시 추출 위치·보정 ID → PDF 페이지·좌표. 좌표의 정밀도도 기록한다. |
| `selection_ledger.jsonl` / `page_coverage.jsonl` | 구간별 채택·제외·중복 사유와 833쪽의 처리 현황 |
| `review_queue.jsonl` | 미결 구간과 판정에 필요한 원문 위치 |
| `manifest.json` / `audit.json` | 입력·코드·설정·출력 해시, 검사 결과, 완료 여부 |
| 검토용 HTML | 청크를 선택하면 보정문·원문 위치·해당 PDF 이미지 영역을 대조할 수 있는 정적 확인 자료 |

본문·제목·조건의 출처 목록은 분리한다. 겹침이나 조건 복사 때문에 한 청크가 여러 원문 위치를 갖는 경우 모든 위치를 보관한다. 하나의 페이지 번호로 대표하여 나머지를 잃지 않도록 한다. 아직 없는 정밀한 글자 좌표를 만들어 내지 않고 기존 블록·줄·셀 좌표의 해상도를 표시한다.

**5. 구현 순서와 완료 판단**

1. 먼저 일반 본문, native/OCR 중복, 이미지 안의 본문, PMCS 이어진 행·경고, 다단 본문, 긴 표, 원문 자체의 불완전 문장으로 작은 검증 표본을 만든다. 기존에 구조가 확인된 PDF 96~118, 272·276, 526~531, 830·854·856쪽 등의 사례를 활용한다. 평가질의의 검색 점수를 보고 표본이나 규칙을 고르지 않는다.
2. 선택·구조·청킹·독립 검증 모듈을 구현하고 표본에서 적용 조건과 출처가 유지되는지 확인한다. 규칙이 충돌하는 사례는 이 단계에서 명시적으로 드러내고 처리 이유를 기록한다.
3. 실험 범위 전체 833쪽에 실행한다. 검토 목록을 처리하고 원문 대조 기록을 남긴다. 자동 프로그램의 완료와 내용 검토 완료를 구분한다.
4. 동일 입력으로 두 번 생성해 주요 출력의 해시를 비교하고 corpus 버전을 고정한다. 이 시점에 corpus가 검색 입력으로 준비되었다고 판정한다.
5. 후속 단계에서 개발용 10문항으로 BGE-M3·FAISS 검색을 점검한다. 최종 60문항은 원문 근거와 청크 조합을 대응시키고 기존 선정 규칙에 따라 고정한다. 검색 성능이 낮다는 이유로 최종 문항을 바꾸지 않는다. 필요한 오류 수정이 생기면 corpus 버전도 함께 갱신한다.
6. 그다음 동일 LLM의 LLM Only/RAG 비교 실행과 평가 프로그램을 구현한다. RAGAS와 발표용 앱은 해당 단계에서 다룬다.

현재 가장 많은 판단이 필요한 부분은 길이 분할 자체보다 본문 선택과 표·조건의 연결이다. 그러므로 ‘청커가 오류 없이 실행되었다’만으로 완료를 선언하지 않고 선택 기록·출처 매핑·원문 대조를 포함해 완료 여부를 판단한다.
