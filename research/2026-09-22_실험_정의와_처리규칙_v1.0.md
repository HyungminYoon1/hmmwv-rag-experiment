# 실험 정의와 처리 규칙 v1.0

작성일: 2026-09-22

전처리·검색·답변 생성과 평가를 구현하기 위한 세부 규칙이다. 기존 모델과 60문항 구성은 유지한다. 모델 비교실험은 아직 수행하지 않았으며, 교범 추출·보정은 아래 2절의 v4 단계까지 진행했다. 실제 모델 파일·패키지 버전·최종 근거 대응표는 예비실험 후 본 실험 전에 고정한다.

이 문서는 2026-09-22 당시의 설계 기록이다. 현재 설정과 결과는 [실험 설계](../docs/experiment-design.md)와 [평가 기록](../experiment/evaluation/RUN_HISTORY.md)에서 확인한다.

## 1. 용어와 평가질의 선정

| 용어 | 정의 |
| --- | --- |
| 근거 단위 | 질문에 필요한 사실·조건·절차를 독립적으로 확인할 수 있는 원문의 의미 단위. 자연스러운 문단·열거·표 행·조건과 지시 항목을 기준으로 하고 해석에 필요한 제목·적용 조건을 함께 보관한다. |
| 필수 답변 요소 | 질문에 답하기 위해 반드시 포함해야 하는 내용. 같은 근거 단위에서 여러 필수 요소가 나올 수 있다. |
| 청크 | 검색기에 저장하는 텍스트 조각. 근거 단위와 독립적으로 식별한다. 하나의 근거가 여러 청크에 걸치거나, 한 청크가 여러 근거를 포함할 수 있다. |
| Oracle Evidence | 검색 결과와 별도로 원문 대조를 통해 사전에 지정한 정답 근거. 조건·단위·적용 차종을 포함한다. |
| 답변불가 | 지정한 corpus만으로 질문의 모든 필수 요구를 충족할 수 없는 상태. 답할 수 있는 부분이 있어도 이 유형에 포함될 수 있다. |

단일 근거와 다중 근거는 필요한 원문 근거 단위가 각각 1개인지 2개 이상인지로 구분한다. 한 문단의 같은 목록에 있는 세 항목을 묻는 질문은 근거 1개·필수 요소 3개일 수 있다. 서로 다른 정비항목의 조건을 비교하는 질문은 근거 2개일 수 있다. 원문 위치, 단위의 경계와 분류 이유를 함께 적어 넓은 범위 전체를 임의로 하나의 근거로 묶지 않는다.

서로 다른 근거가 같은 청크에 들어가도 다중 근거 유형을 유지한다. 청킹 결과만으로 유형을 바꾸지 않는다. 원문 검토에서 필요한 독립 근거의 수가 달라진 것으로 확인될 때만 본 실험 전에 분류를 수정한다. 단일 근거 20개·다중 근거 30개·답변불가 10개의 최종 구성은 유지한다.

최종 문항은 문자 정보만으로 판정할 수 있어야 한다. 그림 해석이나 corpus 밖의 전문적 판단이 필요한 문항은 제외한다. 답변가능 문항은 모든 필수 근거를 충족하는 청크 조합이 최소 하나 있어야 한다. 필요한 최소 청크 수가 5개를 넘는 후보는 본 실험 전에 대체하고 이유를 기록한다. 이 기준은 Top-5에 담을 수 있는 과제로 범위를 정한 것이며, 실제 검색 순위가 낮다는 이유로 문항을 제외하지 않는다.

답변불가 문항에는 결여된 정보, 결여 이유와 확인한 범위, 허용되는 부분 답변 및 관련 원문 근거를 지정한다. 현재 후보 10개는 주로 corpus 밖의 상세 정비·시험절차를 요구하므로 해당 유형의 유보 성능으로 해석한다. 최종 corpus에 정보가 있는데 추출에 실패한 경우는 답변불가로 분류하지 않는다.

## 2. corpus와 청킹

입력은 지정된 TM 9-2320-280-20-1 제1권의 1996년 발행·2004년 Change 2 반영 PDF다. 제1·2장 본문과 문자로 복원 가능한 표를 사용한다. 표지·목차·변경 안내·재배포 안내는 검색 대상에서 제외한다. 원문 인쇄면수와 PDF 순번을 별도로 저장한다.

### PDF 텍스트 추출 오류 보정

원본 PDF와 규칙 기반 추출본은 보존한다. Codex(OpenAI)가 원문 이미지에서 확인한 추출 오류는 대상 레코드·PDF 순번·좌표·수정 전 문자열·수정 후 문자열·문자 위치·사유로 기록한다. 확정한 수정 목록을 일반 프로그램으로 적용하며 문장 요약·번역·정보 추가는 하지 않는다. 그림의 관계나 원문 자체의 오타·수치 문제를 추측하여 고치지 않는다.

사용자가 보정 전후 전체 텍스트를 직접 대조하는 대신, 별도 검증 프로그램이 실제 변경사항과 수정 기록의 일치 여부를 검사한다. 기록 없는 추가·삭제·변경, 미반영 수정, 레코드·출처 정보 변경을 모두 확인한다. 원본·추출본·수정 목록·산출물의 해시와 실제 차이 보고서를 보관하고 같은 추출본과 수정 목록으로 결과를 재생성한다. 보정 적용 실행 중에는 LLM을 호출하지 않는다.

기계 검사는 변경 이력의 일치 여부를 확인하며 원문 의미와의 일치를 판정하지 않는다. Codex의 원문 대조와 연구자의 직접 검증 여부를 구분해 기록한다. 최종 평가질의의 필수 근거 검증 계획은 유지한다. 검색·답변 생성의 로컬 실행과 전처리·평가질의·사후 평가에서의 외부 AI 사용을 구분한다.

2026-09-22 현재 전체 PDF 890쪽의 추출과 702쪽의 OCR 자료 확보를 마쳤다. 검색 대상은 제1·2장인 PDF 순번 31~863쪽, 833쪽이다. 최초 51건 이후 보정을 이어가 누적 수정 기록은 `batch-004` 379건이며, 문자 보정본은 `preprocessing/output/corrected-v4-a`다. 남아 있던 native/OCR 차이 후보 557건은 모두 원문과 대조해 판정을 기록했다. [557건 추가 검토와 보정 결과](../preprocessing/557건_추가검토와_보정결과.md)에 근거와 검증 결과를 보관한다.

표·읽기 순서 및 구간별 채택 규칙은 `preprocessing/review-557/verified-v4-a`에 있다. 이 자료의 PMCS 셀 연결, 표 4개·33행, native/OCR 구간 선택과 중복 방지 규칙을 검색용 corpus 구성에 반영한다. 문자 보정 TXT에는 대안 추출 결과와 표 셀이 함께 있으므로 파일 전체를 그대로 색인하지 않는다. 일부 페이지는 native에 참조문만 있고 본문은 이미지에 있으므로, 페이지 전체를 native로 일괄 대체하지 않는다.

PDF 118쪽의 `Metal particles are`는 원문에서도 불완전하여 원문 그대로 보존하고 충분한 정답 근거로 단독 사용하지 않는다. 같은 페이지의 `Change fluid every 12,000 miles`는 정상적인 명령문으로 유지한다. 구간별 원문 위치와 처리 규칙은 `source118-review.json`에 기록했다.

현재 v4는 확인한 추출 오류를 반영한 보정본이다. 최종 corpus의 본문·표 선택, 청킹, 60문항의 근거 대응표 확정 및 연구자의 필수 근거 검증은 후속 단계다. 재현 실행에는 원본 PDF·고정 OCR 추출본·수정 목록을 사용한다. 같은 입력으로 보정 파일 388개와 구조 파일 19개가 각각 모두 일치했으며, OCR을 새로 계산했을 때의 동일성과는 구분한다.

### 구조 복원과 청킹

1. 페이지별 블록과 좌표로 읽기 순서를 복원한다. 다단·표 때문에 자동 순서가 원문과 다르면 해당 영역의 순서를 수정하고 변경 전후를 기록한다. 줄끝 하이픈과 반복 머리말 제거도 같은 방식으로 기록한다.
2. 장·절 안에서 정비작업·고장진단 항목을 구조단위로 정한다. 독립된 하위 항목이 있으면 그 경계로 구분한다. 다른 구조단위끼리 짧다는 이유로 합치지 않는다. 같은 항목이 페이지를 넘어가면 연결한다.
3. 표는 행별로 열 이름과 값을 연결한다. 표 제목·열 이름·단위·적용 조건을 유지한다. 다른 페이지에 이어지는 같은 표의 반복 제목을 식별하며, 행이 페이지 경계에서 잘렸으면 연결한다. 원문과 대응되지 않는 재구성은 하지 않는다.
4. 청크는 장·절·항목 제목과 표의 반복 설명을 붙인 **최종 검색 텍스트 전체가 500 token 이하**가 되도록 만든다. Qwen3-4B-Instruct-2507 tokenizer를 사용한다. 특수 chat token과 생성 요청용 출처 메타데이터는 청크 길이에 포함하지 않으며, 전체 생성 입력 길이 검사에는 포함한다.
5. 제목과 필요한 반복 설명의 token 수를 먼저 계산하여 본문 예산을 정한다. 한 구조단위가 그 예산을 넘으면 token 창으로 나눈다. 인접 창에는 같은 구조단위의 본문 100 token을 중첩한다. 구조단위 경계에서는 중첩하지 않는다. 마지막 짧은 조각을 다른 구조단위와 합치지 않는다.
6. token 경계가 원문 문자의 일부를 잘라내지 않도록 문자 위치를 함께 보관한다. 경계 보정이 필요한 경우 새 청크의 전체 길이가 500 이하여야 하며, 앞 청크 끝의 본문을 100 token 이상 중첩하는 가장 짧은 문자 경계를 사용하고 실제 중첩 수를 기록한다. 고정 설명이 너무 길어 새 본문을 추가할 수 없거나 길이·문자 보존을 동시에 충족하지 못하면 전처리 오류로 중단한다. 내용을 임의로 삭제해 통과시키지 않는다.
7. 본문·표·고장진단 표본과 평가질의의 모든 근거 구간을 원문과 대조한다. 값·단위·차종·조건·경고의 관계가 유지되는지 확인한다. 포함 범위와 수동 수정 내역을 본 실험 전에 고정한다.

청크 ID는 고정된 corpus의 원문 순서에 따라 `C000001`부터 부여한다. 구조단위 ID, 본문 시작·끝 위치, PDF 순번, 인쇄면수, 검색 텍스트의 token 수와 해시를 저장한다. 청킹 설정이 바뀌면 corpus 버전과 ID 대응표도 새로 만든다.

## 3. 근거 대응표와 검색 점수

질의 i의 필요한 근거 단위 집합을 E_i라 한다. 각 근거 e에 대해 이를 충분히 제공하는 **청크 조합들의 목록** A_e를 만든다. 한 청크로 충분한 경우도 원소가 하나인 조합으로 기록한다.

예를 들어 A_e = {{C000010}, {C000011}, {C000020, C000021}}이면 앞의 두 청크는 각각 단독으로 충분하고, 뒤의 두 청크는 함께 있어야 충분하다. 쉼표로 나열된 청크가 대안인지 동시 필요 조건인지 모호하게 저장하지 않는다.

검색된 상위 5개 ID의 집합을 T_i라고 할 때, A_e 중 어느 한 조합이라도 T_i에 전부 포함되면 e가 검색된 것으로 판정한다. 충족된 근거 단위의 집합을 R_i로 두고 다음과 같이 계산한다.

```text
Evidence Recall@5_i = |E_i ∩ R_i| / |E_i|
Complete Evidence Retrieval@5_i = 1 if E_i ⊆ R_i else 0
```

같은 사실을 반복한 청크를 여러 개 찾았다고 근거 수를 늘리지 않는다. 여러 청크가 필요한 근거에서 일부 청크만 찾으면 그 근거 단위에는 점수를 주지 않는다. 부분 검색으로 확보된 필수 답변 내용은 생성답변의 요소 충족도에서 별도로 관찰한다.

질의별 최소 충분 청크 수는 E_i 전체를 충족하는 조합의 최소 크기로 계산해 저장한다. 다중 근거라도 한 청크로 충분할 수 있다. 서로 같은 원문 근거를 사용하는 문항은 source_group_id로 묶어 표시한다.

검색 지표는 첫 회차의 답변가능 50개에 대해 문항별로 계산해 평균을 낸다. 검색 실행 실패는 검색된 청크가 없는 것으로 두어 0으로 계산하고 실패 건수를 기록한다. 검색은 성공했으나 생성이 실패한 경우 검색 점수는 그대로 유지한다. 답변불가 문항은 이 두 검색 지표의 평균에 포함하지 않는다.

Recall은 **중첩 청크를 동등 근거로 묶어 계산하는 근거 단위 비율**로 정의한다. 같은 근거를 포함한 여러 청크가 검색되어도 그 근거는 한 번만 센다.

## 4. 답변·인용·채점 입력

두 조건은 같은 영어 질문과 공통 프롬프트를 사용한다. RAG context에는 각 청크의 ID·교범·절·페이지와 원문을 제공한다. 출처 표시는 공통 프롬프트의 조건문에서 `[C000123]` 형태로 요구한다. 사용한 여러 출처는 각각 별도의 대괄호로 표시한다.

원문 답변은 그대로 보존한다. 내용 평가용 사본에서는 정규식 `\[C[0-9]{6}\]`에 정확히 맞는 인용 표시만 제거한다. 문장 재작성·요약·사실 교정은 하지 않는다. 두 조건에 같은 처리를 적용하고, 질문이나 실제 기술수치·단위·차종·절 번호는 삭제하지 않는다. 제거 전후 텍스트와 인용 ID를 저장한다. 형식에 맞지 않는 출처 설명은 임의로 지우지 않고 원문에 남긴다.

존재하지 않거나 제공하지 않은 청크를 인용한 경우는 출처 표시 오류로 기록한다. 이 오류를 기술 내용의 진위 점수와 합쳐 새로운 종합점수를 만들지 않는다. 위치 설명만으로 된 문구와 기술 주장은 구분해 판정한다.

필수 답변 요소는 최소 사실·조건·단계로 나누고 요소별로 원문, 적용 조건, 허용 표현·단위와 순서 요구를 기록한다. 질문에 이미 명시된 차종·조건은 답변에서 반복하지 않아도 공유된 것으로 해석한다. 질문에 없고 정답을 제한하는 필수 조건은 답변에 있어야 한다. 같은 요소에 맞는 값과 틀린 값을 함께 제시하면 그 요소는 0이다. 요소 사이의 모순으로 적용 여부가 불명확한 경우에도 충족으로 세지 않는다.

수치의 단위 표기는 사전에 고정한 동의어·환산표를 사용한다. 원문에 병기된 값과 단위는 각각 허용한다. 그 밖의 허용 단위는 고정된 환산계수로 계산한 뒤 답변에 표시된 소수 자릿수로 반올림한 값과 비교한다. 원문과 같은 단위의 임의적인 수치 변경이나 공학적 허용오차를 추가하지 않는다. 정성적 ‘약’이라는 표현만으로 오차 범위를 넓히지 않는다. 질문에서 단위가 명시되지 않았고 단위 구분이 필요한 수치에는 답변의 단위가 필요하다.

## 5. 지표 정의와 평가 유효성

### Answer Relevancy

배포 버전을 고정한 RAGAS의 해당 클래스를 사용하고 strictness=3으로 설정한다. 평가용 BGE-M3는 고정한 동일 revision의 dense vector를 사용한다. 재구성 질문과 유보성 판정, 임베딩 유사도와 라이브러리 원점수를 저장한다. 이 점수는 사실 정확도나 정답률이 아니다.

세 번의 유보성 판정이 모두 1이면 원점수를 0으로, 그렇지 않으면 세 cosine similarity의 평균으로 계산한다. 이 규칙에 맞는 RAGAS 배포 버전과 클래스를 선정하고 개발용 질의로 확인한다. 임의로 단순 유사도만 계산해 같은 이름으로 보고하지 않는다. 부분 유보가 포함된 답변은 원점수와 유보성 판정을 함께 보아 점수의 원인을 해석한다. [공식 설명](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/answer_relevance/), [이 규칙을 확인한 공식 구현](https://github.com/vibrantlabsai/ragas/blob/298b68274234c060deacab3cf5fb52aa3a20e885/src/ragas/metrics/collections/answer_relevancy/metric.py)

평가 출력은 재구성 질문 3개가 모두 비어 있지 않고, 유보성 필드가 유효하며, 점수가 유한수일 때 유효하다. 유효성 검사를 통과하지 못하면 라이브러리가 0을 반환했더라도 평가 실패로 처리한다. cosine similarity 값을 임의로 0~1 범위로 잘라 바꾸지 않는다.

생성이 실패하거나 평가용 본문이 비어 있으면 RAGAS를 호출하지 않는다. 라이브러리 원점수 ar_raw는 해당 없음으로 저장하고, 시스템 비교용 ar_report는 0으로 둔다. 정상 답변에는 ar_report=ar_raw를 적용한다. Answer Relevancy 보고값은 **생성 실패 0을 포함한 집계**임을 밝히고 정상 응답의 원점수 평균과 건수도 보관한다. 평가 API 실패에는 이 0 규칙을 적용하지 않는다.

### 사실적 주장과 근거 지원

질문과 내용 평가용 답변만으로 사실적 주장을 분해하고 중복을 제거한다. 이 추출 단계에는 Top-5 문맥과 Oracle 근거를 주지 않는다. 조건·부정·단위·대상·절차 순서가 주장과 분리되지 않도록 한다. 동일 답변의 주장 목록 C_i는 한 번 생성해 저장하고 실제 검색문맥과 Oracle 근거의 두 지원 판정에 공통으로 사용한다. RAGAS의 주장 분해·지원 판정 구성요소를 사용하고, 인용 제거·주장 목록 공유·중복 처리·실패 집계는 연구의 처리 규칙으로 명시한다. 구현에서 평가모델 입력·출력과 claim ID를 기록한다.

- RAGAS Faithfulness: C_i 중 실제 제공한 Top-5 문맥으로 지지되는 비율. 답변가능 50개의 RAG 답변에 적용한다.
- Oracle Evidence Support Score: C_i 중 사전에 확정한 Oracle 근거로 지지되는 비율. 답변가능 50개의 두 조건에 적용한다.
- Required Answer Coverage: 사전에 정한 필수 요소 중 정확히 충족한 요소의 비율. 답변가능 50개의 두 조건에 적용한다.

실제 검색문맥과 Oracle 근거는 바꾸어 넣지 않는다. Oracle에 없는 추가 주장에는 ‘기준 근거 미지원’을 부여한다. 이를 교범 전체나 현실에서 거짓으로 확정한 것으로 표현하지 않는다. Oracle 지원도는 내용 누락을 직접 측정하지 않으므로 요소 충족도와 함께 해석한다. [Faithfulness 정의](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/)

채점 응답에는 claim/element ID, 0 또는 1, 판단한 원문 위치와 짧은 이유를 요구한다. ID 누락·중복·잘못된 범위는 평가 실패다. 정상적인 기술 답변에서 주장 추출이 빈 목록을 반환하면 평가 실패로 처리한다. 전체 유보·질문과 무관한 거절처럼 실제 사실 주장이 없는 경우는 해당 없음과 0을 아래 표대로 구분한다.

## 6. 실패·유보·결측 처리표

상태는 실행 결과와 답변 내용으로 나누어 기록한다. 실행 결과는 OK, GEN_EMPTY, GEN_TIMEOUT, GEN_ERROR로 구분한다. GEN_EMPTY에는 공백뿐인 답변과 인용 표시를 제거하면 본문이 없는 답변을 포함한다. GEN_ERROR에는 검색 실패인지 생성 실패인지 하위 원인을 기록한다. 아직 시도하지 않은 요청은 NOT_RUN이며 실패율의 분모에 넣지 않는다. 본 실험의 완료 여부는 예정한 요청이 모두 시도되었는지 따로 확인한다.

정상 응답의 내용은 일반 답변, 부분 답변과 유보, 전체 유보, 무관한 거절로 표시한다. 근거 없는 보완·인용 오류·길이 제한 도달 등은 함께 붙일 수 있는 별도 태그다. 512 token에 도달해 반환된 비어 있지 않은 응답은 그대로 평가하고 길이 제한 태그를 남긴다.

다음 표의 품질 지표는 답변가능 50문항에 적용한다.

| 상태 | ar_report | Oracle 지원도 | 요소 충족도 | RAG Faithfulness | 답변가능 문항의 전체 유보 판정 |
| --- | --- | --- | --- | --- | --- |
| 정상 답변 | 유효 원점수 | 주장별 비율 | 요소별 비율 | 주장별 비율 | 0 |
| 부분 답변과 유보 | 유효 원점수 | 실제 주장으로 계산 | 맞은 요소만 인정 | 실제 주장으로 계산 | 0, 부분 유보 별도 집계 |
| 전체 유보이며 사실 주장 없음 | 유효 원점수 | 0 | 0 | N/A_NO_CLAIM | 1 |
| 무관한 거절이며 사실 주장 없음 | 유효 원점수 | 0 | 0 | N/A_NO_CLAIM | 0, 무관한 거절 별도 집계 |
| 생성 실패·시간초과·빈 응답 | 0, ar_raw는 N/A | 0 | 0 | N/A_NO_RESPONSE | 0, 실행 실패 별도 집계 |
| 정상 답변의 특정 평가만 실패 | 그 지표만 N/A_EVAL_ERROR | 그 지표만 N/A_EVAL_ERROR | 그 지표만 N/A_EVAL_ERROR | 그 지표만 N/A_EVAL_ERROR | 유보 판정이 실패한 경우만 N/A_EVAL_ERROR |

전체 유보라고 말하면서 사실적 내용을 덧붙인 경우에는 해당 주장을 평가하고, 기술 내용을 제공했는지에 따라 부분 답변·근거 없는 보완 태그를 붙인다. 단순히 ‘모르겠다’라는 문자열이 포함되었다고 자동으로 전체 유보로 분류하지 않는다.

답변불가 10문항에는 위 네 내용 품질 지표를 적용하지 않고 N/A_OUT_OF_SCOPE로 남긴다. RAG는 결여된 정보를 명시하고 근거 없는 보완 없이 전체 또는 부분 유보를 했으면 Correct Abstention=1이다. 허용 부분 답변은 문항별 허용 범위와 실제 제공된 문맥 양쪽으로 지지되어야 한다. 빈 답변·무관한 거절·생성 실패는 0이다.

LLM Only의 Corpus-Unanswerable Abstention은 요구된 미확인 부분을 명시적으로 유보했는지로 판정한다. RAG의 적절성 점수와 같은 정답률로 비교하지 않는다. 유보 문구 뒤에 그 미확인 부분을 사실로 채워 넣으면 명시적인 유보로 인정하지 않는다. corpus 밖 지식의 사실성은 이 비율로 판단하지 않는다.

평가 API·파싱·의미 유효성 검사 실패는 같은 입력으로 최대 2회 재시도한다. 최초 호출을 포함해 최대 3회이며 모든 시도를 저장한다. 같은 입력·버전의 첫 유효 결과를 사용한다. 끝내 유효하지 않으면 해당 지표만 평가 결측으로 둔다. 이 규칙은 같은 호출을 성공할 때까지 반복하는 것을 허용하지 않는다.

평가 결측이 없으면 품질 지표의 분모는 50, 답변가능 전체 유보율의 분모는 50, 답변불가 지표의 분모는 10이다. 다만 Faithfulness는 사실 주장이 있는 유효 답변만 분모에 포함하고, 해당 없음의 사유별 건수를 함께 보고한다. 평가 결측이 있으면 지표별 유효 분모와 원래 문항 수를 함께 제시한다. 예를 들어 유효 9개 중 7개면 ‘7/9, 평가 가능 9/10’으로 보고하며 결측 1개를 오답으로 간주하지 않는다. 두 조건의 공통 품질 지표 차이는 양쪽 모두 점수가 있는 동일 문항으로만 계산한다. 시스템 생성 실패에 사전 부여한 0은 유효 점수이므로 이 공통 집합에 포함한다. 유효 분모나 시간 비교 대상이 0개이면 통계값은 집계 불가로 표시하고 수치를 만들지 않는다.

필수 근거 데이터가 없거나 설정·실행 코드가 잘못된 경우는 성능 실패로 채점하지 않는다. 해당 실험의 유효성을 점검하고 수정 사유·영향 범위·버전을 기록한다. 최종 결과에 어느 실행을 사용했는지 명시한다.

## 7. 수동 검증 40개

최종 질의 확정 후 단일 근거 4개와 다중 근거 6개를 기존의 PCG64(seed 42) 방식으로 뽑는다. 두 조건의 첫 회차 답변 20개와 답변불가 10문항의 두 조건 답변 20개를 합쳐 40개로 유지한다.

1. 답변가능 20개: Oracle 근거에 대한 주장별 지지와 필수 요소별 충족을 확인한다.
2. 그중 RAG 10개: 모델에 실제 제공한 Top-5 문맥으로 Faithfulness 판정을 추가 확인한다.
3. 답변가능 표본의 Answer Relevancy: 재구성 질문과 유보성 판정이 답변 내용을 반영하는지 확인한다. 사람이 임의로 동일한 cosine 점수를 매기는 검증은 하지 않는다.
4. 답변불가 20개: 전체·부분 유보, 미확인 부분, 근거 없는 보완 및 부분 답변의 허용 범위를 확인한다.

조건명과 자동점수를 가린 뒤 원문에 따른 판정을 먼저 작성한다. 이후 지표별 일치·불일치와 원인을 기록한다. 인용 방식으로 조건을 짐작할 수 있는 점은 기록한다.

수동 점수는 자동점수의 검증 자료다. 검증한 일부만 수동 점수로 바꾸어 전체 자동평가 평균에 섞지 않는다. 채점 코드·프롬프트의 구현 오류를 고치면 영향받는 해당 지표의 전체 답변을 같은 규칙으로 다시 평가한다. 판정 기준 자체의 사후 변경은 별도 분석으로 표시한다. 연구자 원문 대조를 독립된 정비 전문가 검증으로 표현하지 않는다.

## 8. 시간·메모리 측정과 집계

회차당 60문항 × 2조건, 총 3회 360개 요청을 수행한다. 품질·검색의 주 분석은 첫 회차를 사용한다. 개발용 질의로 조건별 5회 워밍업한 뒤 측정한다. 답변이 달라져도 나중 회차의 좋은 답변으로 바꾸지 않는다.

생성모델은 keep_alive=-1로 유지하고 검색모델·인덱스도 상주시킨다. 요청마다 대화 이력이나 답변 결과를 재사용하지 않는다. 런타임의 prefix/KV 캐시는 같은 설정으로 유지하며 이를 사용한 워밍업 후 성능으로 보고한다. 서로 다른 입력이 같은 캐시 적중률을 보장한다고 가정하지 않는다. 지원되는 경우 load_duration과 prompt_eval_cached_count를 기록하고, 지원하지 않는 항목은 측정 불가로 표시한다. [Ollama FAQ](https://docs.ollama.com/faq), [API 반환 항목](https://docs.ollama.com/api/generate)

시간 측정 시작 전 모델 상주 상태와 모니터링 PID를 확인한다. RAG는 질의 임베딩 직전, LLM Only는 공통 입력 구성 직전에 시계를 시작하여 정상 응답 전체가 수신될 때 종료한다. RAG retrieval에는 질의 임베딩·검색·청크 조회·문맥 구성을, generation에는 요청 구성·전송·입력 처리·전체 생성을 포함한다. 경계 밖의 제어 오버헤드가 있으면 전체 시간과 두 구성요소의 합 차이도 기록한다.

생성 요청 제한시간은 기존의 300초다. 실패·시간초과 응답을 진단 목적으로 재시도한 결과는 원래 측정에 섞지 않는다. 다음 요청 전에 이전 생성과 대기 요청이 종료되었는지 확인한다. 종료 여부를 확인할 수 없으면 실행을 중단하고, 원인 정리와 양쪽 조건의 재워밍업 후 아직 시도하지 않은 요청부터 이어간다. 실패한 요청의 기록과 점수는 보존한다. 아직 시도하지 않은 요청은 실패로 세지 않는다.

예기치 않은 모델 재로딩이나 측정 중 다른 작업의 개입이 확인된 실행은 시간 측정 이상으로 표시한다. load_duration이 0보다 크다는 사실만으로 재로딩을 단정하지 않고 상주 상태·PID·실행 로그와 대조한다. 해당 질의의 시간 비교 포함 여부는 두 조건에서 동일하게 처리한다.

시간 비교에는 두 조건 모두 세 회차에서 비어 있지 않은 응답을 정상 반환했고 측정 이상이 없는 공통 질의만 사용한다. 내용상 오답이나 전체 유보라는 이유로 시간 비교에서 제외하지 않는다. 질의별 세 시간의 중앙값을 먼저 구하고 그 대표값들의 중앙값과 p95를 계산한다. p95는 오름차순 대표값 x의 h=(n-1)×0.95에서 아래·위 순번 사이를 선형 보간한다. 표에는 **‘질의별 3회 중앙값의 median/p95’**라고 표시한다. 전체 개별 요청의 p95로 표현하지 않는다. 제외 건수·원인과 성공·시간초과 건수를 함께 보고한다.

RSS는 해당 조건에 필요한 실행기·Ollama 서버와 모델 실행 프로세스, RAG 검색 프로세스 및 관련 자식 PID의 합계를 100 ms 간격으로 측정한다. 같은 PID는 한 번만 센다. VRAM은 장치 전체 사용량을 같은 주기로 측정한다. 요청 직전 유휴값은 1초 동안 수집한 표본의 중앙값, 요청 처리 중 값은 수집한 표본의 최대값으로 정한다. 유휴값 수집은 응답시간에 포함하지 않는다.

Peak RAM·Peak VRAM은 세 회차의 측정 가능한 모든 시도에서 관측한 요청별 최대값 중 조건별 최대값이다. 실패·시간초과에서 수집한 표본도 포함하고 유효 기록 수를 밝힌다. Idle VRAM은 요청별 유휴 중앙값의 조건별 중앙값이다. RSS 합계는 공유 메모리 중복 가능성이 있는 프로세스 관측값이며 시스템 전체의 순수 물리 RAM 소비량으로 해석하지 않는다. 100 ms 사이의 순간 최대 사용량까지 검증했다고 주장하지 않는다.

## 9. 본 실험 전 확정할 산출물

- corpus 범위·구조단위·전처리 변경 내역, 청크 ID·원문 위치·token 수·해시.
- 최종 60문항과 별도 개발용 10문항, 근거 단위·필수 요소·충분 청크 조합·최소 청크 수·공유 근거 문항군.
- 문항별 허용 표현·수치·단위·조건·순서·부분 답변 범위와 판정 예시.
- 공통 생성 프롬프트와 평가 프롬프트, 지표 버전·클래스·유효성 검사·실패 처리 규칙.
- 모델·tokenizer·임베딩 revision과 파일 해시, 실제 서버·패키지·드라이버 버전, CPU thread·캐시·GPU 배치 설정.
- 첫 회차 순서와 회차별 조건 순서, 수동 검증 표본, 실행·평가·측정 상태별 로그 형식.

예비실험은 길이 초과·표 복원·실행 상태·채점 형식을 확인하는 단계다. 모델의 최종 60문항 점수를 보고 설정을 조정하지 않는다. 최종 산출물과 설정을 검증한 뒤 버전과 해시를 부여하여 본 실험을 시작한다.

## 10. 규칙 선택의 근거

| 쟁점 | 선택한 규칙 | 이유·영향 |
| --- | --- | --- |
| 한 청크에 여러 근거가 있는 문항 | 유형 유지, 최소 청크 수 별도 기록 | 청킹 때문에 질문의 의미적 유형이 바뀌는 문제를 방지한다. |
| 청크 비율과 근거 비율 | 근거 단위 Recall로 통일 | 중첩 청크를 중복 정답으로 세지 않는다. |
| 빈 응답의 관련성 집계 | 원점수는 해당 없음, 시스템 집계는 0 | 라이브러리 점수와 연구의 실패 처리 관례를 구분한다. |
| 평가 API 실패 | 지표별 결측·유효 분모 공개 | 측정 실패를 오답으로 바꾸지 않는다. |
| 수동 검증 | 기존 40개 안에서 지표별 범위 명시 | 표본을 늘리지 않고 Oracle와 Top-5 문맥의 검증을 분리한다. |
| 청크 예산 | 제목·표 설명까지 500 token에 포함 | 제목을 붙인 뒤 길이 제한을 넘는 모순을 해소한다. |
| 시간·자원 대표값 | 질의별 세 시간의 중앙값 분포, 메모리는 관측 최대값 | 표와 본문에서 서로 다른 통계량을 같은 이름으로 부르는 문제를 방지한다. |

이 단계에서는 규칙 간 일관성을 검토했다. 개별 60문항의 최종 정답 근거·청크 매핑, 자동평가 연동과 실제 실행 성능은 이후 단계의 검증 대상이다.
