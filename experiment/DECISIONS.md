# 실험 결정 기록

## E01. 기존 검색 결과의 재현성 보존

- 맥락: 기존 인덱스는 파이프라인 파일과 패키지 해시가 고정돼 있다.
- 선택지: retrieval 내부 개편 / 별도 실험 모듈에서 기존 코어 재사용.
- 결정: 후자. 원래 개발용 검색 차단은 유지하고 실험 전용 worker를 둔다.
- 이유: 검증된 검색 방법을 바꾸지 않고 정식 실험을 구분한다.
- 파일: architecture.md, worker.py, runner.py.
- 후속 확인: 본 실험 전 원래 파일의 해시와 전체 재계산 PASS 확인.

## E02. 문항 유지와 근거 정교화

- 맥락: 사용자는 60문항을 유지하기로 했다. 예전 규칙의 5청크 초과 후보 자동 대체 조항은 최근 지시와 다르다.
- 선택지: 자동 대체 / 원문·범위를 먼저 검토하고 결함 보고.
- 결정: 질문·유형을 보존한다. 충분 청크 조합을 AND/OR로 기록하고 복합 채점 요소를 분리한다. 5청크 초과만으로 대체하지 않는다.
- 이유: 검색 성능을 보고 평가문항을 바꾸는 것을 방지한다.
- 파일: annotations.py, gold.py, gold-v1/.
- 후속 확인: 연구자 직접 검증은 Codex 대조와 별도로 기록한다. 직접 확인 완료 전 최종 평가 확정은 하지 않는다.

## E06. 개발 단계 공통 프롬프트 수정

- 맥락: pilot-v1의 LLM Only 10개가 모두 유보했다. 해당 프롬프트는 대상 차량·교범을 알려주지 않았고, 모델이 문맥 없음 표시를 답변 불가로 취급하는 정황이 있었다. 개발 문항 4개의 별도 진단에서도 차량을 모르는 일반 자동차 답변이 나타났다.
- 선택지: 그대로 본 실험 / LLM Only에만 별도 지시 / 양쪽 조건에 같은 차량·교범 식별정보와 문맥 사용 규칙 제공.
- 결정: 세 번째. 두 조건의 공통 프롬프트에 HMMWV와 교범 식별정보를 넣고, 발췌가 없을 때 기존 모델 지식으로 답하도록 명시한다. 빈 문맥 표시는 `[No manual excerpts supplied. Answer from existing model knowledge.]`로 통일한다. 질문·정답·검색 설정은 변경하지 않는다.
- 이유: 질문이 가리키는 문서를 두 조건 모두 식별할 수 있게 한다. 문맥이 없다는 사실만으로 유보하도록 유도하지 않는다. 채점 결과를 높이는 방향으로 문항별 프롬프트를 만들지 않는다.
- 파일: prompt.txt, generation.py, runner.py. 최초 설정은 archive/pilot-v1-config, 개발 진단 전체 입력·출력은 reports/prompt-diagnostic*.json에 보존한다.
- 후속 확인: 수정한 설정으로 개발용 10문항을 다시 점검한 후 고정한다. 본 실험 60문항의 답변은 이 결정 이전에 생성하지 않았다. 문서 미제공에 따른 유보 자체를 오류로 단정하지 않으며 내용 평가는 사후 별도로 수행한다.

## E07. 생성 수집과 사후 품질 평가의 분리

- 맥락: 외부 평가 API 설정과 연구자의 직접 근거 검토가 아직 없다. 사용자는 실험 실행을 승인했다.
- 선택지: 모든 작업 보류 / 근거·생성 설정을 고정하고 로컬 실행 결과부터 수집.
- 결정: 후자. 검색·생성·시간·자원 결과를 수집하되 RAGAS 및 최종 품질 평가는 NOT_RUN으로 둔다. 연구자 검토 전 검색 점수는 잠정 결과로 표시한다.
- 이유: API 연결 여부와 무관하게 로컬 비교는 수행할 수 있다. 연구자 확인이나 자동평가를 대신했다고 주장하지 않는다.

- 후속 확인: 자동평가 모델·배포 버전·세부 프롬프트 확정은 별도 평가 실행에 앞서 기록한다. 생성 결과를 이미 수집한 뒤 확정한 항목을 사전 확정으로 표현하지 않는다. 기존 규칙 9절의 일괄 사전 확정에서 이 부분이 달라졌음을 실험 방법 기록에 명시한다.

## E13. API 가상 사례 점검 중 저장 오류와 검산 기록 보완 (2026-09-28)

- 맥락: sol-smoke-20260928-v1에서 실제 API 응답을 받았으나 파일 교체 시 PermissionError 1건과 RAGAS 관련성 점수 검산 불일치 1건이 발생했다. 같은 응답을 재사용한 오프라인 재검산에서는 불일치가 재현되지 않았다. 가상 사례를 본 평가에 포함하지 않는다.
- 선택지: 파일 오류에 모델을 재호출 / 저장만 재시도, 검산 허용 오차 확대 / 기존 허용 오차를 유지하고 수치·벡터 해시 기록 추가.
- 결정: 원본과 실행 기록을 백업·보존한다. 파일 교체만 제한적으로 재시도하고 계속 실패하면 평가를 중단한다. 응답 저장 후 중단된 단계는 저장된 응답을 검증해 복구한다. 검산 허용 오차 1e-10, 평가 모델·프롬프트·채점 규칙은 유지하고 새 가상 사례 실행으로 확인한다.
- 이유: 로컬 저장 실패가 추가 유료 호출을 유발하지 않게 하고, 재현되지 않은 검산 문제의 원인을 임의로 단정하지 않는다. 재실행에서 원래 점수를 선택적으로 덮어쓰지 않는다.
- 파일: evaluation/common.py, judge.py, engine.py, tests/test_evaluation.py, verification/sol-ar-diagnostic.json. 변경 전 파일은 backups/before-sol-runtime-fix-20260928에 보관한다.
- 후속 확인: 새 가상 사례에서 오류가 없고 기준 사례의 판정이 맞으면 고정된 본 평가를 시작한다. 수치 불일치가 다시 발생하면 저장된 진단 값으로 원인을 확인한다.

### E13 추가: 수치 검산의 독립 구현

- sol-smoke-20260928-v2에서도 첫 답변의 RAGAS 점수 0.9717807311과 보조 검산 0.9557113285가 달랐다. 저장된 같은 벡터에 대해 오프라인에서 NumPy와 Python math.fsum으로 다시 계산하면 모두 0.9717807311이 나온다. 실시간 경로에서만 나타난 차이의 구체적 원인은 확인하지 못했다.
- 보조 검산을 NumPy의 별도 호출에서 Python math.fsum 기반 코사인 계산으로 교체한다. RAGAS의 원래 계산, 점수 의미, 허용 오차 1e-10은 그대로 둔다. 서로 다른 구현을 대조하여 수치 불일치가 통과하지 않도록 한다. 가상 사례의 API 호출 기록은 그대로 보존하고 새 버전으로 검증한다.
- 변경 전 파일은 backups/before-sol-reference-check-20260928, 진단 값은 evaluation/verification/sol-v2-numeric-diagnostic.json에 남긴다. 본 평가를 시작하기 전에 새 검산 방식을 실제 API 경로에서 확인한다.

- 후속 확인 결과: sol-smoke-20260928-v3은 API 응답 17회로 가상 사례 3개 모두 정상 완료했다. 정답 사례의 지지·충실·요소 점수는 1, 오답 사례는 0, 답변불가 유보는 1이며 수치 검산 차이는 1.11e-16이었다. 관련 검사 32개 통과 후 sol-formal-20260928-v1의 첫 회차 120답변 평가를 시작했다. 기존 두 실패 기록도 보존한다.

## E14. 저장된 역질문과 벡터를 이용한 관련성 점수 재계산 (2026-09-28)

- 맥락: 본 평가 M02 LLM Only에서 관련성 검산 차이 0.018561이 발생했다. LLM 호출이 없는 별도 검사에서도 같은 입력 배열이 변하지 않았는데 NumPy dot 결과가 달라지는 현상을 재현했다. 스레드 수·CPU 커널 선택을 바꾼 진단에서도 해결되지 않았다. 원인이 라이브러리 결함인지 장치·런타임 상태인지까지는 확인되지 않았다.
- 선택지: 결측 유지 / 같은 모델로 다시 채점 / 저장된 최초 유효 판정과 벡터에서 계산만 다시 수행.
- 결정: 세 번째. 진행 중인 API 수집·기존 파일은 유지한다. 수집 완료 후 답변 가능한 모든 문항에 같은 계산식을 일괄 적용한 별도 파생 실행을 만든다. RAGAS가 생성한 역질문 3개와 noncommittal 판정, 기존 BGE 벡터를 그대로 사용한다. 코사인 유사도는 Python math.fsum과 50자리 Decimal 두 구현으로 계산하여 1e-10 이내 일치를 요구한다. 모델 재호출·역질문 선택·프롬프트 변경은 하지 않는다. 다른 자동평가 오류는 그대로 결측으로 둔다.
- 이유: 수치 연산 오류의 보정과 모델의 재판정을 구분한다. 원래 결과·오류·벡터·API 응답을 보존하고 모든 답변에 같은 계산을 적용하여 점수가 유리한 사례만 골라 바꾸는 일을 막는다.
- 파일: evaluation/verification/recalculate_relevancy.py, numeric-bad-operations.json, numeric-runtime-settings-30k.json, 원래 sol-formal-20260928-v1과 별도 파생 실행 폴더. 파생 실행의 manifest에 원본 파일 해시·계산 코드·변경 항목을 기록한다.
- 후속 확인: 두 수치 구현의 일치, 원래 지지·요소·유보 판정의 불변, 유효 답변 수·짝비교 재집계를 검사한다. 실험 기록에는 RAGAS 역질문 생성과 동일한 관련성 계산식을 사용하되 코사인 계산은 독립 구현으로 재계산했다고 명시한다. 기존 corpus·검색·생성 기록은 변경하지 않는다. 이번 오류로 과거 검색 수치가 틀렸다고 단정하지 않는다.

- 재계산 출처 기록 보완: 첫 파생 실행은 중복 호출 점검과 겹쳐 원본 summary.json의 집계 시각이 바뀌면서 해시 검증에 실패했다. 원래 모델 응답·벡터는 바뀌지 않았다. 후속 수치 검증은 통과했지만, 집계 재생성만으로 과거 결과의 검증이 깨지지 않도록 summary와 계산 스크립트를 파생 실행 안에 사본으로 고정했다. 원본 manifest·입력·응답·벡터는 계속 실제 파일 해시로 검증한다. 이전 파생 실행은 실패/이전 기록으로 보존하며 최종 파생 실행 ID는 sol-formal-20260928-numeric-v3이다. 이 과정의 API 호출은 0회다.

- E14 최종 확인: 120답변 정상 집계, 관련성 100개 재계산, 최종 평가 오류 0건. Decimal 대조 최대 차이 3.33e-16, 출처 해시 1,950개와 코드 16개 확인. 다른 지표의 판정 불변 및 원본 report 재생성 후 출처 검증 유지도 확인했다. 사람의 정답 근거 확인과 40답변 대조는 PENDING으로 남긴다.
